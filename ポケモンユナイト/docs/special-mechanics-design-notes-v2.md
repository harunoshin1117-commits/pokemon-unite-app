# 特殊効果 設計メモ v2

このメモは `special-mechanics-inventory-v2.json` と `mechanics-effects-survey-v2` をもとにしたドラフトです。旧調査よりも、技単位ではなく効果単位の分解を優先しています。

## v2で変えた抽出ルール

- すべての特性・通常攻撃・強化攻撃・技・ユナイト技を `sourceEntry` として残す。
- 特殊効果が0件のソースも削除しない。
- 直接ダメージと単純移動は `baseAction` に保存し、特殊効果件数には含めない。
- やけど、スロウ、スタック、HP参照などは説明文内から個別効果として分解する。
- `battleState` は必要理由を `battleStateReasons` として分けて保存する。

## 設計上の示唆

- 単発ダメージ計算に必要なもの、攻撃順計算に必要なもの、完全な戦闘再現に必要なものを分ける必要がある。
- 状態異常やバフは、式データとは別に状態管理データとして扱う方がよい。
- エースバーンの火種のような対象別スタックは `targetState.stacks` が必要。
- 技使用後の次通常攻撃強化は `attackerState.nextBoostedAttackReady` のような攻撃側状態が必要。
- 単純移動は計算対象外にし、無敵・妨害無効・再使用などが付いたときだけ特殊効果として扱うのがよい。

## 人間確認の優先順位

1. v2で特殊効果0件になったソースが本当に単純ダメージ/単純移動だけか確認する。
2. やけど、どく、まひ、スロウなど状態異常の抽出漏れを確認する。
3. スタック・マーク・ゲージ系の保持者と対象を確認する。
4. HP参照ダメージの参照タイミングと上限適用範囲を確認する。
5. `battleStateReasons` が広すぎないか確認する。

## 既知の限界

- Unite-DBの説明文を機械的に分解しているため、誤検出や過検出が残る。
- 日本語訳は機械要約であり、公式訳ではない。
- 処理順、丸め順、スタック余剰、時間更新は人間確認が必要。
- v2も実装仕様ではなく、設計材料として扱う。
