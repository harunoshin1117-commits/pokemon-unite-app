# Claude Review Context

この文書は、Claude無料版にレビューや設計相談を依頼するときに一緒に渡す共通コンテキストです。

## プロジェクト概要

このプロジェクトは、ポケモンユナイトのダメージ計算サイトです。ユーザーは攻撃側ポケモン、防御側ポケモン、レベル、技、通常攻撃、持ち物などを選び、ダメージ結果を確認します。

Claudeは実装担当ではなく、外部レビュー担当・設計相談相手として使います。コードを書かせるのではなく、設計・責務分離・やりすぎ・UI/UX・将来拡張性を確認してもらいます。

## 重要方針

- Codexが実装と差分作成を担当する。
- Claudeはレビュー、設計相談、UI/UX確認だけを担当する。
- Claudeには大量コードを丸ごと貼らず、変更要約、重要差分、確認観点を中心に渡す。
- 未確認のゲーム仕様は、確定値としてアプリ実装に入れない。
- 人間が検証した値を段階的に `pokemonData.js` へ反映する。
- 調査データ、アプリ実装データ、計算ロジック、UI表示を混ぜすぎない。
- 既存UIや既存計算結果を変える場合は、理由とリスクを明確にする。

## 現在の主な構成

- `js/app.js`: DOMイベント、状態取得、計算呼び出し、描画呼び出しをつなぐ接続役。
- `js/damageCalculator.js`: ダメージ計算の中心。DOMを直接参照しない。
- `js/pokemonData.js`: ポケモン、ステータス、技、通常攻撃、計算用データ。
- `js/battleState.js`: 将来の攻撃順や詳細モードに向けた戦闘状態の土台。
- `js/resultRenderer.js`: 計算結果の画面表示。
- `js/heldItemService.js`: 持ち物補正の計算・集計。
- `docs/project-map.md`: 作業入口の地図。
- `docs/project-overview.md`: 現在の構成、主要関数、設計メモ。
- `データリサーチ/*.json`: 調査データ。未確認値や候補値を含む。

## データ形式の注意

- `pokemonData.js` には旧形式と新形式が混在している。
- 旧形式は `formula` / `formulaPlus` を使う。
- 新形式は `damageComponents` / `plusDamageComponents` / `additionalDamageEffects` を使う。
- ピカチュウなど一部の通常攻撃は `normalAttack.basic` / `normalAttack.boosted` の数値データ参照へ移行している。
- エレキボールのように相手の減少HPを参照する追加効果がある。
- 攻撃順、HP引き継ぎ、シールド、回復、バフ・デバフ、スタック、継続ダメージ、効果時間、相手ごとの状態は将来の完全再現に向けた重要テーマ。

## Claudeに見てほしい共通観点

1. 要件を正しく満たしているか。
2. 未確認仕様を確定扱いしていないか。
3. 調査データと実装データが混ざっていないか。
4. 既存機能を壊す可能性がないか。
5. 元データや既存状態を直接変更していないか。
6. 新旧データ形式の分岐が正しく維持されているか。
7. ポケモン固有処理を増やしすぎていないか。
8. 将来100体以上へ展開したときに破綻しないか。
9. 将来の攻撃順・シナリオ機能と矛盾しないか。
10. 状態管理を不適切な場所へ入れていないか。
11. データ、計算ロジック、UIの責務が混ざっていないか。
12. テストが実装内容を追認するだけになっていないか。
13. 境界値、例外、条件分岐のテストが不足していないか。
14. ドキュメントと実装に食い違いがないか。
15. 今回は動いても、次の実装で作り直しになりそうな点がないか。

## Claudeへの禁止事項

- 実装コードを書かせない。
- 追加実装を直接依頼しない。
- 大量のコード全体を読ませる前提にしない。
- 未確認仕様を確定値として扱わせない。
- Codexの報告を正しい前提でレビューさせない。

## Claudeの回答でほしい粒度

- 問題がある場合は、重要度順に書く。
- 「今すぐ直すべき点」と「後回しでよい点」を分ける。
- 設計相談では、メリット、リスク、代替案を簡潔に出す。
- PRレビューでは、問題ない点も明示する。
- UI/UXレビューでは、ユーザーが迷う箇所と優先修正だけを具体化する。
