## 見つかった効果パターン候補

- 相手スタック / マーク系
  - 対象ごとの状態管理が必要。
  - 例: エースバーンの火種、ギルガルドのマークや強化回数系、多くの技で付与されるマーク。
- 自分スタック / ゲージ系
  - 攻撃側が保持する状態が必要。
  - チャージ、ゲージ、強化攻撃、フォーム、モード切り替えなどでよく出る。
- 時間制バフ / デバフ系
  - 持続時間の管理が必要。
  - 移動速度、攻撃速度、防御変化、シールド、ユナイト技後のバフなどでよく出る。
- 次の通常攻撃強化 / 強化攻撃予約系
  - 攻撃順の管理が必要。
  - 現在の単発ヒット数UIだけでは正確に表現しにくい。
- HP条件 / HP参照系
  - 現在HP、最大HP、減少HP、対象HPなどを正しいタイミングで参照する必要がある。
  - 参照タイミングは実測するまで未確認として扱う。
- 回復 / シールド系
  - 現在HPとシールドHPの状態管理が必要。
  - 最大HP増加を追跡する必要がある効果もある。
- 野生ポケモン限定処理
  - 対象タイプの判定が必要。
  - 上限が合計ダメージにかかるのか、式の一部にだけかかるのかを明示する必要がある。

## 設計案A: 効果コンポーネントをデータ駆動で表現する

多くの効果を `damageComponents`、`additionalDamageEffects`、`buffEffects`、`stackEffects`、`shieldEffects` のような構造化データとして表現する案。

向いているもの:
- 標準的なダメージ
- HP参照ダメージ
- 単純なバフ/デバフ
- 式が分かっているシールドや回復

リスク:
- タイミング規則までデータへ押し込むと読みにくくなる。
- スタック更新、余剰、消費ルールが抽象的になりすぎる。

## 設計案B: イベント処理 + battleState

戦闘中の行動を順番付きイベントとして処理する案。

イベント例:
- `normalAttack`
- `boostedNormalAttack`
- `move`
- `uniteMove`
- `timeElapsed`
- `ko`
- `assist`

必要になりそうな状態:
- `attackerState.currentHp`
- `attackerState.cooldowns`
- `attackerState.buffs`
- `attackerState.gauges`
- `targetState.currentHp`
- `targetState.shields`
- `targetState.debuffs`
- `targetState.stacks`

向いているもの:
- エースバーンの火種
- 技使用後に次の通常攻撃が強化される効果
- 持続時間付きバフ
- 対象ごとのスタック
- KO/アシスト連動効果

リスク:
- 設計変更が大きい。
- シナリオUIができるまでは、現在の単発計算画面とは分けて考える必要がある。

## 設計案C: 共通コア + 専用例外

単純な効果は共通データで扱い、特殊すぎるものだけポケモン専用処理へ逃がす案。

向いているもの:
- 普通のダメージ、バフ、デバフはデータ駆動のまま扱える。
- 共有スキーマを無理に曲げず、特殊ギミックを隔離できる。

リスク:
- 専用処理が増えすぎると保守が難しくなる。
- どの効果を例外扱いにするか、ルールが必要。

## 現時点のおすすめ

ハイブリッド案がよさそうです。

1. 単純な式はデータに置く。
2. 攻撃順や時間に依存する効果は共通イベント処理へ寄せる。
3. 状態は `battleState` に保存する。
4. 共通処理で表現しにくいものだけ専用処理にする。

この形なら `pokemonData.js` を読みやすく保ちつつ、将来的に実戦に近い再現へ進めやすいです。

## 人間確認の優先順位

1. 生成された各ポケモンの調査ファイルが、重要な特殊効果を拾えているか確認する。
2. `battleState` の形に影響するため、相手スタック系と自分ゲージ系を優先して確認する。
3. ダメージ実装前に、HP参照タイミングと野生ポケモン上限を確認する。
4. 時間管理実装前に、持続時間の更新とスタック余剰ルールを確認する。
5. 純粋なデータで済む効果と、イベント処理が必要な効果を分ける。
